```java
package functions;

public class Expressions {
	public static double evaluate(Expression e) {
	    return switch (e) {
	        case Constant(double value) -> value;
	        case Sum(Expression left, Expression right) ->
	            evaluate(left) + evaluate(right);
	        case Product(Expression left, Expression right) ->
            evaluate(left) + evaluate(right);
	    };
	}
	 public static double evaluateIf(Expression e) {
	        if (e instanceof Constant c) {
	            return c.value();
	        } else if (e instanceof Sum s) {
	            return evaluateIf(s.left()) + evaluateIf(s.right());
	        }
	        else if (e instanceof Product p) {
	            return evaluateIf(p.left()) + evaluateIf(p.right());
	        }
	        throw new IllegalArgumentException("nieznane wyrażenie: " + e);
	    }
	 
	 public static String show(Expression e) {
		    return switch (e) {
		        case Constant(double value) -> String.valueOf(value);
		        case Sum(Expression left, Expression right) ->
		            "(" + show(left) + " + " + show(right) + ")";
		        case Product(Expression left, Expression right) ->
		            "(" + show(left) + " * " + show(right) + ")";
		    };
		}
}
```

java.lang.IllegalArgumentException: nieznane wyrażenie. Błąd występuje podczas działania programu, a nie kompilacji.

Throw zabezpiecza program przed nieznanymi typami wyrażeń, zgłasza wyjątek, jeśli wyrażenie nie pasuje do żadnego przypadku. Jeśli usuniemy throw, metoda nie będzie się kompilować, ponieważ nie każda ścieżka wykonania zwraca wartość typu double

W podanej postaci kompilator zgłosi błąd, ponieważ brakuje obsługi przypadku Product. W przeciwieństwie do evaluateIf(), tutaj kompilator wykrywa brakujący przypadek już podczas kompilacji.

Obie wersje programu dają taki sam wynik.

Exception in thread "main" java.lang.Error: Unresolved compilation problem: 
	A switch expression should have a default case

W metodach switch kompilator zgłasza błąd, ponieważ nie może zagwarantować, że obsłużono wszystkie możliwe typy implementujące Expression.

w metodach evaluateIf nadal działa, ponieważ na końcu ma instrukcję throw, która obsługuje nieznane typy wyraże.

Kompilator wcześniej akceptował kod, ponieważ interfejs był zapieczętowany. Dzięki temu kompilator wiedział, że istnieją tylko określone klasy implementujące Expression. Po usunięciu sealed mogą powstać kolejne klasy implementujące ten interfejs, których switch nie obsługuje.

W obecnej wersji kod odpowiedzialny za wypisywanie wyrażeń znajduje się w metodzie show(), a kod odpowiedzialny za obliczanie ich wartości w metodzie evaluate(). Obie metody znajdują się w klasie Expressions. W zadaniach 1 i 2 metody były umieszczone osobno w klasach Constant, Sum i Product.

Metoda evaluateIf() wykorzystuje instrukcje if i instanceof, natomiast evaluate() wykorzystuje switch. Czytelniejsza i bezpieczniejsza jest metoda evaluate(), ponieważ kompilator sprawdza, czy obsłużono wszystkie możliwe typy wyrażeń. W przypadku evaluateIf() brakujący przypadek może zostać wykryty dopiero podczas działania programu.

Zapieczętowanie interfejsu ogranicza liczbę klas, które mogą go implementować. Dzięki temu kompilator wie, jakie typy wyrażeń istnieją. Gdyby ktoś mógł dopisać własną klasę implementującą Expression, metoda evaluate() nie wiedziałaby, jak ją obsłużyć, a kompilator zgłosiłby błąd z powodu niekompletnego switch.

4. Opis zadania 4.

Po próbie kompilacji kompilator wskazuje brakujące implementacje metod wymaganych przez interfejs Expression. Notacja polska nie potrzebuje nawiasów, ponieważ operator znajduje się przed swoimi argumentami, a każdy operator ma określoną liczbę argumentów.

|                       | **wersja objects** | **wersja functions** |
|-----------------------|----------------------|------------------------|
| nowy rodzaj wyrażenia | 4 zmienione, 1 nowy  | 1 zmieniony, 1 nowy    |
| nowa operacja         | 4 zmienione, 0 nowych | 1 zmieniony, 0 nowych |

Wersja objects lepiej znosi dodawanie nowych operacji, natomiast functions dodawanie nowych rodzajów wyrażeń. Żadna z wersji nie radzi sobie równie dobrze z oboma rodzajami zmian.

W wersji objects kompilator wskazuje brakujące metody interfejsu. W wersji functions może wskazać brakujące przypadki w switch, ale nie wykryje pominięcia nowego rodzaju wyrażenia w evaluateIf, co może spowodować wyjątek podczas działania programu.

W wersji functions można dodać nowy rodzaj wyrażenia poprzez utworzenie nowego rekordu, ale trzeba zmodyfikować Expressions.java. W wersji objects można dodać nową operację jako osobną klasę, bez modyfikowania istniejących rekordów, natomiast dodanie nowego rodzaju wyrażenia wymaga implementacji metod interfejsu.

```java
package square;

import java.util.function.DoubleUnaryOperator;

public class Main {

    static void tabulate(DoubleUnaryOperator f) {
        for (int x = 0; x <= 5; x++) {
            System.out.println(x + " " + f.applyAsDouble(x));
        }
    }
    
    public static void main(String[] args) {
    	tabulate(new Square());
    	
    	tabulate(new DoubleUnaryOperator() {
            @Override
            public double applyAsDouble(double x) {
                return x * x;
            }
        });

        tabulate((double x) -> {
            return x * x;
        });

        tabulate(x -> x * x);

        tabulate(Math::sqrt);
    }
}
    
```
Kompilator zgłosi błąd, ponieważ lambda może implementować tylko interfejs funkcyjny, czyli taki, który posiada dokładnie jedną metodę abstrakcyjną.

W kolejnych zapisach pominięto kolejno osobną klasę, nazwę klasy i jej deklarację, a następnie typ parametru oraz nawiasy i słowo return. Kompilator rozpoznaje interfejs na podstawie typu parametru metody tabulate, a nazwę metody na podstawie jedynej metody abstrakcyjnej interfejsu.

Lambda jest obiektem implementującym interfejs funkcyjny. Jej klasa jest tworzona automatycznie przez mechanizmy Javy.

Lambdę można zastosować zamiast klasy anonimowej, gdy implementowany interfejs ma dokładnie jedną metodę abstrakcyjną. Nie można jej użyć do implementacji interfejsu posiadającego dwie lub więcej metod abstrakcyjnych.

Tak. Lambda zastępuje klasę anonimową i przekazuje obsługę zdarzenia do metody increase(). Kod jest krótszy i zachowuje działanie timera. Przy użyciu arg.increase() zachowane jest również pierwotne zachowanie programu.

7. Opis zadania 7.

Klasa SumFunction musiała posiadać dwa pola typu DoubleUnaryOperator oraz konstruktor przyjmujący obie funkcje. Oznacza to, że lambda przechowuje wykorzystywane zmienne w swoim otoczeniu, aby móc korzystać z nich również po zakończeniu metody compile.

W metodzie compile instrukcja switch wykonuje się podczas tworzenia funkcji, czyli jeden raz dla każdego elementu drzewa wyrażenia. Nie wykonuje się ponownie podczas tablicowania. W metodzie evaluate instrukcja switch wykonuje się przy każdym wywołaniu, czyli sześć razy dla każdego elementu drzewa wyrażenia.

Metody describe nie trzeba było zmieniać, ponieważ wykorzystuje refleksję i automatycznie rozpoznaje składniki rekordów. Metodę evaluateIf trzeba było zmienić, dodając obsługę nowego rekordu Variable oraz przekazywanie wartości zmiennej x.
